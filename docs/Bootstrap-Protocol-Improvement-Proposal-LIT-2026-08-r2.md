## Tier 1 — trivial cost, adopt first

### LIT-01 — No-lossy-rewrite preservation invariant
**Source:** P1 RQ1 (a reorganizing pass silently condenses content unless one preservation instruction is added; REALTALK correctness nearly halves under condensation, 77.6 → 41.2), corroborated by arXiv 2605.12978. This is a relative comparison, immune to P1's judge-reliability problem — but **[PAR-10]** it is not uniform: P1's own data shows the sign flips by benchmark. Preserving wins on LoCoMo (82.9 vs 79.1), REALTALK (77.6 vs 41.2), and PersonaMem-128k (59.5 vs 54.8); **condensing wins on PersonaMem-32k (68.8 vs 56.2)**, where a tighter store is easier to search — P1 calls this the clearest sign no single compression policy is right everywhere.
**Why the invariant escapes the counter-benchmark [PAR-10]:** the drafted invariant is deliberately narrower than P1's "keep every fact" prompt. It preserves *facts, flags, and citations* and explicitly permits dropping prose — so the tightening that won on PersonaMem-32k remains legal under it. The invariant forbids the failure mode (silent fact loss), not the compression.
**Affects:** `/checkpoint` skill, `progress.md` contract (GR2-01 text), `learnings/` discipline, and any consolidation pass (operator-run or auto-memory).
**Change (draft normative sentence):** *"Any rewrite or summarization of an existing memory artifact must preserve every load-bearing fact — decisions, failed approaches with their do-not-retry flags, source locators and citations — or link to it. Condensation may drop prose; it may never drop a fact, a flag, or a citation."* Register one Assumption-Ledger row: the invariant compensates for current-generation condensation tendency; re-validate on model change.
**Risk & mitigation:** over-preservation bloat. Bounded by the existing compose-do-not-fork lint (link, don't inline) and by LIT-02's consolidation path for deliberate size reduction.

### LIT-04 — Lexical-first retrieval guardrail
**Source:** P2's one surviving lesson: single-vector semantic retrieval has a hard ceiling on exact/combinatorial recall (BM25 93.6 vs E5-Mistral 8.3 Recall@100 on LIMIT-full; both verified); lexical and multi-vector methods do not share the ceiling. Adopted *without* P2's contested causal framing — and the guardrail survives under **both** P2 and its rebuttal, since it is an operational rule for governance-fact recall, not a claim about why single-vector fails.
**Affects:** Phase 6.5 `tools.md` guidance (Claude Context recommendation; optional memory-MCP note).
**Change (draft):** *"Exact recall — which files reference a spec, which decisions touched X, secret-path matching — must use lexical or pointer retrieval (grep/ripgrep, `.claude/specs/INDEX.md`), never single-vector semantic search alone. Claude Context remains recommended for fuzzy code discovery on large codebases, paired with a lexical fallback. A vector-backed memory MCP, if ever installed, is a fuzzy supplement — never the system of record for governance facts."* **[PAR-09, optional upgrade adopted]** Add one clause: *"If a vector layer is ever chosen, prefer late-interaction/multi-vector or hybrid backends over single-vector"* — the rebuttal shows multi-vector models are dramatically stronger and forgetting-robust on exactly this task class.
**Risk:** none identified; the protocol already leans this way. The change makes the lean a stated rule.

### LIT-05 — Tool-harness store-shaping annotation
**Source:** P1 RQ5 (replacing the tool set reshapes the memory store as strongly as swapping the model — abstract-verbatim), independently corroborated by P3's harness-modularity observations. **[PAR — W-1 demoted]** The protocol's [W-1] worktree/gate finding is a *see-also* (another case of harness components composing non-neutrally), not a corroborator — it concerns gate fail-open, not store shape.
**Affects:** Phase 6.5 `tools.md`; a see-also cross-reference at [W-1].
**Change (draft):** *"The tool harness shapes the memory store as strongly as the model does. Changing search or edit tooling is a store-affecting decision, not a neutral convenience — record it the way a model change is recorded."*
**Risk:** none; documentation only.

### LIT-10 — Small-model single-step invariant
**Source:** P3 F3: SC-CoT collapses on small models via instruction-adherence/parsing failure (verbatim-supported), and PoT bottlenecks on small-model codegen (verbatim-supported). **[PAR-07]** The "≥7B-or-reasoning-model floor" is **this proposal's synthesis, not P3's statement**: P3 tested below 7B (Qwen2-1.5B, Qwen2-0.5B) and found deepseek-r1-1.5B — a 1.5B *reasoning* model — outperforming InternLM2.5-7B-Chat. The floor is constructed from sub-7B instruct weakness plus that reasoning-model exception, and is labeled as inference.
**Affects:** Phase 9.6; Companion "Model Assignment Strategy."
**Change (draft):** *"Haiku-tier components get single-step, schema-constrained jobs only — never multi-step scaffolds."* The protocol already behaves this way (structured `{verdict, reason}` judge output, iteration-summary enforcement hook, retry-once-then-halt); this elevates the behavior from accident of design to stated invariant, so future edits cannot regress it silently.
**Risk:** none; codifies existing behavior.

## Tier 2 — low cost, high compounding value

### LIT-07 — Decouple prompt-visible framing from harness-enforced iteration caps **[reworked per PAR-01/02/03/11]**
**Source [PAR-02 — corrected attribution]:** P3 F1 (ReAct-Pro): with the harness capping steps at 10 (Appendix A parameter, not surfaced to the model) while the prompt said the model could take as many steps as needed, AQuA moved **40.16 → 64.57** on GPT-3.5 — the only ablation that isolates the sentence. GSM8K's 38.13 → 74.91 bundles the two-call split with the sentence and is not cited for the sentence alone. Note honestly: P3's winning sentence was **factually false in its own configuration** (the model could not take unlimited steps); this port does not reproduce the falsehood — see (c) below. Converges with the "context anxiety" lineage the protocol's v2.3.0 note cites (Cognition's term, per the GAR correction).
**Gap [PAR-11 — corrected scope]:** in Phase 9.5, the wrapper primes "the task definition itself," and every loop-eligible task definition carries `loop_max_iterations` — the cap is always prompt-visible there. In Phase 9.6 the gap exists **only for eligible-for-both tasks** (goal-supervised-only tasks have `loop_eligible: false` and therefore carry no `loop_max_iterations` field at all; goal mode's own `max_iterations` lives unprimed in `goal-config.md`). The inverse-of-winning-configuration claim holds for 9.5 always and 9.6 conditionally.
**Change [PAR-01 — re-scoped as a wrapper-contract change, not "priming-list text"]:**
(a) Redact `loop_max_iterations` from the primed task-definition slice: amend the Phase 9.5 step 3 priming enumeration and the Phase 9.6 goal-loop priming enumeration, **and add a fifth item to the B-1 deliverable contract's binding comment enumeration** requiring the operator-completed iteration loop to filter the field from the primed copy. Enforcement stays wrapper-only, unchanged. The field **stays in the task-definition schema** and in the committed task file — this is a priming-slice change, not a schema change.
(b) **Migration [PAR-01a]:** existing installs have operator-completed loops that prime the unfiltered task definition. The fold must state the migration explicitly: on adoption, the operator edits their completed `loop.sh`/`goal-loop.sh` priming assembly to apply the filter; an unedited install keeps the old behavior, and the changelog entry must say so, so no committed doc describes a behavior the install does not perform.
(c) **Priming sentence [PAR-03 — reworded to be fully true]:** *"Don't ration or count iterations; the harness manages all budgets and will end the loop when appropriate."* The r1 sentence ("Take as many iterations as the task needs") was not literally true — the harness stops at the cap whether or not the task needs more — and adopting a knowingly-overclaiming assurance would set the precedent the protocol's honest-artifact discipline exists to prevent.
(d) **Deliberate-absence note [PAR-03, W-1 pattern]:** the why-redacted rationale is recorded operator-visibly — a comment block in `loop-config.md`/`goal-config.md` and one sentence in the Phase 9.5 doc text — so a future maintainer can tell a deliberate absence from an oversight and does not "fix" the unfiltered task definition back into priming.
(e) **Honest scope [PAR-01b]:** redaction reduces *prompt salience* of the cap; it does not hide the cap from an agent that goes looking. The cap remains workspace-readable in the committed task file (which the implementer's Phase 7 description directs it to read), in committed `loop-config.md`/`goal-config.md`, and — after LIT-08 — in `learnings/mode-selection.md`. P3's configuration had a harness-side cap genuinely out of the model's reach; this port approximates it at the priming layer only. The budget-anxiety mechanism is prompt-salience-driven, so the approximation is expected to carry most of the effect — that expectation is itself part of the ledger row below.
(f) One Assumption-Ledger row: redaction compensates for current-generation budget-anxiety behavior; calibrated against the current tier; re-validate on any pinned-model change — a model generation that plans *better* with a known budget flips this default.
**Doctrinal consistency:** Phase 9.5 already holds that max-iterations is the safety net, not the success signal; withholding the cap from the primed slice, while it stays truthful in every committed artifact, is defensible non-disclosure consistent with that doctrine (adversarial-review lens-4 ruling, PAR-03).
**Classification [PAR-01c]:** this is the fold's one **behavioral priming change** — subtractive on the primed surface, contract-amending for the wrappers. It is excluded from the "additive" count in the aggregate header. MINOR treatment stands per the v2.7.0 precedent.
**Risk:** stale effect size (GPT-3.5-era, math tasks, AQuA-only isolation); direction could invert on future models; unedited legacy installs silently keep old behavior (mitigated by the stated migration step and changelog entry). Ledger row plus LIT-06 golden runs are the detectors.

### LIT-03 — Verbatim-vs-distilled retention routing rule
**Source:** P1 RQ2 (a verbatim episode log serves a strong consumer best; distilled guidance serves a weak one; "consumers of memory" is P1's own framing). **[PAR-08]** The two halves have unequal support per P1's own sign tests: the weak-consumer half (distilled beats verbatim at gpt-4.1-mini: net +14, p≈0.02) is solid; the strong-consumer half (episode log over distilled at gpt-4.1: net +7, p≈0.23) is, in P1's words, suggestive at best. The load-bearing half of this routing rule — don't feed raw trajectories to the weak judge tier — is the well-supported one.
**Affects:** Phase 9.5 (GR2-02 trajectory-retention text); Phase 7 artifact-role descriptions.
**Change (draft):** *"Verbatim artifacts — `trajectory-<task>-<iter>.jsonl`, raw checkpoints — serve strong consumers: the operator, or a full-strength model doing forensic resume. Distilled artifacts — `decisions.md`, `learnings/`, the checkpoint synopsis — serve weak or cheap consumers: Haiku-tier priming and autonomous-loop re-priming. Route by consumer strength; do not feed raw trajectories to the judge tier or force the operator to reconstruct from synopses."* The protocol already produces both artifact classes; this adds the missing routing rule so the token economics are deliberate.
**Risk:** none; documentation of intent over existing artifacts.

### LIT-09 — Complexity-downgrade rule for the calibration review
**Source:** P3 F2 (complexity is an error-accumulation tax; "carefully evaluating the actual benefits of each added complexity"), corroborated by P3's frontier-model result (strong models gain least from scaffolds).
**Affects:** the calibration-review skill (Phase 9.6 calibration mechanism).
**Change:** add one rule: each scaffold layer must pay for itself in the ledger. If the ~20-entry review shows no case where the goal-supervised judge's verdict diverged usefully from the deterministic gates, the review proposes downgrading that task class to loop mode; the same test applies one level down (loop mode vs operator-only-with-gates). **[PAR — disambiguator added]** "Usefully diverged" is judged with the mode-selection template's *"yes but the judge was noisy"* field, not raw divergence counts — divergence alone cannot separate judge-caught-a-real-issue from judge-was-wrong, which is precisely the distinction the `goal-condition-suspect` halt exists to surface. Recommendations, not decisions — the operator approves, mirroring the trust ramp's posture in the opposite direction. Depends on LIT-08's fields for the divergence evidence.
**Risk:** premature downgrade off a small sample; mitigated by the existing ~20-entry threshold and operator veto.

### LIT-08 — Four-metric calibration-ledger standardization
**Source:** P3 F4 (accuracy / cost / token usage / pass rate as first-class metrics; score-vs-cost frontier; pass rate — the proportion of valid, non-empty predictions — as the leading indicator of model/scaffold mismatch).
**Affects:** `learnings/mode-selection.md` entry template (Phase 9.6 calibration mechanism); reads from wrapper-emitted fields.
**Change:** extend the per-task entry with four recorded fields: **outcome** (terminal-success vs halt class, from `halt_reason`), **tokens**, **iterations used vs cap**, **format-validity rate** (from `summary_failure_count`). **[PAR-12 — field-existence precision]** The elapsed/turns/tokens/evaluator-calls enumeration is promised for `goal-loop.sh`'s `loop-final`; Phase 9.5's loop-mode `loop-final` promises the iteration history and the Trajectory line but does not name a tokens field — for loop-mode rows, tokens come from the retained trajectory JSONL or are recorded as unavailable. `summary_failure_count` exists only in goal-supervised mode; format-validity is structurally **N/A** for loop-mode rows, and the template says so rather than implying uniform recordability. **[PAR-05 — TEL-01 positioning]** This transcription is the telemetry-off path: when the operator has opted into TEL-01, `.claude/steering/telemetry.md` already names `claude_code.token.usage` sliced by `agent.name` as queryable evidence, and the review may query instead of transcribe — one evidence channel, stated, not two unreconciled ones. The ~20-entry calibration review can then run a per-project score-vs-cost comparison across mode×model pairs — the right-sized private version of P3's leaderboard.
**Risk:** minor operator recording burden; mitigated because the values are wrapper-emitted or trajectory-derivable — this is transcription, not new instrumentation.

## Tier 3 — medium cost, build once, two consumers

### LIT-06 — Golden-task regression harness
**Source:** P3's ProgrammaticClient pattern (batch test definitions → automated scoring), fused with the regression-set requirement of LIT-02. One mechanism, two consumers.
**Affects:** Assumption Ledger (re-validation triggers); Phase 9 (smoke-test tasks as natural seeds); LIT-02's promote gate.
**Change:** a small committed golden set (2–3 known-good, loop-eligible, trivially revertible tasks, seeded from Phase 9 smoke tasks). On any Assumption-Ledger trigger (pinned-model or runtime-floor change), the operator re-runs the set **through each *enabled* autonomous mode [PAR-06 — scoped]** and compares LIT-08's four metrics against a stored baseline — converting the ledger's current fail-loud *notice* into a *measurement*. **Golden runs carry their own iteration cap of 2–3 [PAR-06]** — a golden task that needs more iterations *is* the regression signal, and the cap bounds the cost. **Stated cost [PAR-06]:** worst case ≈ 3 tasks × enabled modes × 2–3 iterations of full priming per trigger — real but bounded tokens; the operator should know this before adopting. **[PAR-05 — TEL-01 positioning]** For telemetry-on operators, TEL-01 already supplies *cost-shape* evidence for two ledger rows; golden runs are the behavioral complement (does the loop still converge?), not a duplicate channel. The same runs serve as LIT-02's pre/post consolidation check. **[GR2-06 note]** No collision with GR2-06 (different mechanism); note only that the runtime-floor change the owed seam re-cut would produce is itself a golden-run trigger.
**Risk:** maintenance load of the golden set (staleness as the codebase moves). Mitigation: seed from Phase 9 smoke tasks, cap the set at 3, and treat golden-set drift as an ordinary spec-versioning event.

### LIT-02 — Reversible, eval-gated memory consolidation
**Source:** P1 RQ4 (taxonomy adherence erodes as stores grow; only the strongest management model sustains it — while noting, per the honesty header, that P1 also found stores stay *useful* within its one-conversation horizon) plus arXiv 2605.12978 (verified): continuous LLM rewrite degrades a store unless preservation-constrained, reversible, and explicitly gated.
**Affects:** Phase 7 (`learnings/` discipline), Phase 10 handoff checklist, any auto-memory usage. Written vendor-neutral: it constrains *any* consolidation mechanism.
**Scope [PAR-04 — artifact named precisely]:** consolidation targets **`.claude/learnings/`** (and its README convention). `.claude/specs/INDEX.md` is the living *task board*, not a memory index — it is **out of consolidation scope** and is never reorganized by this procedure. (The protocol has no separate memory-index artifact; r1's "learnings/ + INDEX.md" pairing was the ambiguity.)
**Change:** an operator-run consolidation procedure (skill or Phase 10 checklist step): (1) **snapshot = a git commit (or tag) of the pre-consolidation state [PAR-04]** — `learnings/` is a committed directory, so git is the snapshot and `git revert` is the rollback; no filesystem copy is parked anywhere the 7-day state purge or the GR2-02 log-pruning obligation could reach, because no filesystem copy exists; (2) reorganize into a parallel copy — never in place; (3) diff for dropped facts against LIT-01's invariant; (4) run the LIT-06 golden set against both stores; (5) promote only if the new store scores no worse — **ties promote [PAR-04, stated]**, acceptable solely because the git snapshot makes every promotion reversible; retain the pre-consolidation commit reference in the promotion's decision-log entry until operator approval. Trigger guidance: when `learnings/` or `sessions/` growth starts crowding `/resume` context.
**Risk:** the eval gate is only as good as the golden set (small-N; noise can pass a tie). Acceptable: the gate's job is catching gross degradation, and the git snapshot makes every promotion reversible regardless.

## Rejections — evaluated, not compatible or not helpful

Recorded with the same weight as the adoptions, per the operator's instruction: nothing was forced to fit. All six were tested symmetrically in review and upheld.

- **REJ-A — Auto-reorganizing taxonomy / management-agent hierarchy (P1's ambitious reading).** P1's own data: only the strongest management model sustains taxonomy adherence, and organization buys search-cost economy, *not* answer quality. Wrong trade for a solo, possibly mixed-model operator. Revisit only if a top-tier management model is standardized *and* a measured retrieval-cost problem exists.
- **REJ-B — Embedding-dimensionality as a design driver (P2's causal framing).** Directly contested by arXiv 2603.29519 — **[PAR-09, corrected]** whose argument is that **LIMIT itself is k=2 row-sparse**, so by Alon et al. embeddings of dimension 5 suffice for it, defeating P2's dimensionality explanation *on its own dataset*; the high-sign-rank worst-case matrices are the ones the rebuttal says may not arise in practical settings. Domain shift and relevance-misalignment are the operative causes; finetuning mitigates. Only LIT-04's narrow guardrail survives (and survives under both papers).
- **REJ-C — The reasoning-algorithm operator library (P3: ToT, GoT, RAP, DnC, PoT, SC-CoT).** Rejected on P3's own evidence: underperforms CoT on cost-adjusted accuracy; RAP/DnC excluded by the authors for token blowup (verbatim); frontier models — the tier the protocol pins — gain least and sometimes lose (verbatim). PoT is subsumed by Claude Code's native code execution plus deterministic gates (a stronger verifier). SC-CoT's voting is dominated by the protocol's verify-don't-vote gate philosophy; its one defensible echo already exists as operator-initiated `--investigate-disagreement`.
- **REJ-D — Conductor DAG engine, async distributed execution, WebPageClient, public leaderboard (P3).** Category mismatch for a solo markdown-and-shell operator. The DAG semantics already exist natively: `backlog.md` + `blocked_by` + ready-to-run determination + worktree parallelism. Observability is already right-sized by the TEL-01 telemetry surface. LIT-08 is the right-sized replacement for the leaderboard.
- **REJ-E — Two-call Think/Act micro-mechanism (P3 ReAct-Pro, structural half).** Already embodied at macro scale (spec → implement phase separation; the 9.6 iteration-summary reflect step) and superseded at micro scale by native extended thinking. Importing the two-call structure would add a model-call per step for a mechanism the substrate provides. **[PAR-02 note]** The structural half contributed the 34.25 → 40.16 AQuA gain — real, and part of why LIT-07 must not claim GSM8K's undecomposed delta for the sentence.
- **REJ-F — All vision content of P3** (V*, SEAL, VWM, ZoomEye, MME-RealWorld results). Excluded by operator instruction; also independently irrelevant to a text-and-code governance protocol.

## Dependencies and suggested adoption order

LIT-01, -04, -05, -10 have no dependencies — adoptable immediately as a Tier-1 batch. LIT-03 is an independent one-edit item. **LIT-07 is no longer a one-edit item [PAR-01]:** it carries the binding-comment-contract amendment and the migration step, and should be adopted as its own deliberate slice within the fold. LIT-08 precedes LIT-09 (the downgrade rule consumes LIT-08's fields). LIT-06 precedes LIT-02 (the consolidation gate consumes the golden set). Nothing here blocks, or is blocked by, any **open** B-series, G-1, or GR2 item; **LIT-07 does amend the text derived from B-1** — which is *adopted*, not open — by extending the binding comment enumeration from four items to five.

## Standing caveats for the adopting session

Every adoption above inherits its source paper's evidence limits: P1 is unreplicated and pre-peer-review with a bounded horizon; P2's theorem is sound but its practical reach is contested; P3's magnitudes are stale by two model generations, and only AQuA isolates LIT-07's mechanism. Nine proposals are cheap to reverse (doc text, ledger rows, git-snapshotted procedures); LIT-07 is reversible but requires the same migration path in reverse. None changes gate semantics, the wire surface, the state schema, or the task-definition schema. Where a proposal encodes a model-generation-dependent bet (LIT-01, LIT-07), the Assumption Ledger row is the designed expiry mechanism.
